# PactFlow 项目介绍与面试问答

> 面向 AI（人工智能）产品经理岗位的项目复习材料  
> 项目地址 <https://github.com/yuey0420/PactFlow>  
> 项目性质 独立完成

## 一 项目定位

PactFlow 是一个契约约束下的透明可控 Agent Runtime（智能体运行时）。我关注的问题是 Agent（智能体）获得文件、Shell（命令行）和动态 Skill（技能）等执行能力后，如何约束它的操作范围，如何留下可追溯的过程证据，以及如何判断任务是否真正完成。

我在模型和工具之间加入流程治理层，将任务目标、资源权限、工具策略、审批条件和验收规则写入结构化任务契约。系统在执行前生成计划，在工具调用前判断权限，在高风险动作处暂停审批，并在执行后根据证据生成验收结果。

PactFlow 的主要价值可以概括为三点。

- Agent（智能体）的权限边界由运行时规则执行，减少对提示词自律的依赖。
- 复杂任务可以形成可持久化的任务 DAG（有向无环任务图），便于查看依赖、状态和执行记录。
- 任务结果由契约规则和运行证据共同判断，降低模型自报完成带来的不确定性。

## 三 三种运行模式

### chat（对话模式）

面向普通问答和轻量交互。该模式不启用任务拆解，优先保持响应速度。工具调用仍受现有工具策略和安全边界约束。

### development（开发模式）

面向代码、文件处理和多步骤自动化任务。系统默认调用模型规划器，把目标拆成有依赖关系的子任务，再按依赖顺序推进。规划失败时会回退到确定性拆解，避免流程直接中断。

### audited（审计模式）

面向需要更强证据和变更核对的任务。该模式保留开发模式的规划能力，并增加文件系统基线、checkpoint（检查点）、执行后差异计算和变更对账。高风险动作是否需要人工批准，仍由任务契约和工具策略决定。

三种模式共用同一套工具守卫、运行账本和验收机制。模式负责选择流程强度，契约负责定义具体权限。

## 四 核心设计

### 1 统一工具网关

内置工具和动态 Skill（技能）最终接入 `ContractToolNode`（契约工具节点）。每次调用都会经过契约守卫，检查工具是否允许、目标资源是否在范围内、调用次数是否超过限制，以及当前风险级别是否需要批准。

权限判断位于模型之外。即使模型生成了越权参数，工具网关也可以拒绝执行并记录原因。

### 2 Skill（技能）检索与 help → run 两阶段调用

技能调用部分包含两套相互配合的机制。

- Skill 检索（技能检索）负责从大量技能中找到合适候选，解决“应该使用哪个技能”的问题。
- help → run（先查看说明，再执行）负责选中技能后的说明披露和安全执行，解决“这个技能能否执行、应该怎样执行”的问题。

两套机制可以串联使用，也可以根据技能数量和风险等级缩短路径。

#### 第一套机制 Skill 检索（技能检索）

技能数量增加后，把所有说明一次性放入模型上下文会增加上下文消耗，也会干扰能力选择。我为技能增加了 Skill Registry（技能注册表）和轻量 Manifest（能力清单）。能力清单记录名称、描述、标签、依赖工具、风险等级和可信等级。

系统启动时先扫描这些轻量信息，根据用户目标从技能注册表中检索少量候选技能，需要完整说明时再加载 `SKILL.md`。已加载内容使用 LRU（最近最少使用）缓存管理。

当前检索采用关键词、词元重合和子串匹配排序。它没有使用 Embedding（向量嵌入）或向量数据库，因此更准确的名称是元数据检索或候选召回，不应直接称为 RAG（检索增强生成）。

能力清单属于检索后的轻量预览。它帮助模型判断候选技能是否合适，但不会授予执行权限。

#### 第二套机制 help → run 两阶段调用

选中技能后，模型可以先调用 help（查看完整说明），了解技能能力、使用方式和风险，再调用 run（申请执行）。这套两阶段调用让模型在执行前获得完整信息并重新判断，降低直接执行不熟悉技能的风险。

系统根据风险和可信度决定 help 是否强制。

- low（低风险）且 trusted（可信）或 verified（已验证）的技能可以直接申请 run。
- 其他低风险和 medium（中风险）技能需要先查看能力清单或完整 help。
- high（高风险）和 critical（关键风险）技能必须先调用 help，再申请 run。

从产品概念上看，这里只有“技能检索”和“help → run 两阶段调用”两套机制。从实现接口看，技能提供 manifest（查看能力清单）、help（查看完整说明）、run（申请执行）三种模式，其中 manifest 属于检索和预览环节，help 与 run 组成两阶段调用。

无论采用哪条路径，run 都只是执行申请，最终仍要通过任务契约、工具守卫和必要的人工审批。

高风险技能的完整路径如下。

```text
技能注册表检索候选
→ 能力清单轻量预览
→ help 查看完整说明
→ run 申请执行
→ 契约守卫判断
```

低风险且可信的技能可以使用较短路径。

```text
技能注册表检索候选
→ run 申请执行
→ 契约守卫判断
```

如果技能数量很少并且名称已经明确，也可以不先进行技能注册表检索，直接进入 help → run。检索解决选择问题，两阶段调用解决执行前披露问题。

### 3 模型规划器与任务 DAG（有向无环任务图）

development（开发模式）和 audited（审计模式）默认使用模型规划器。规划器接收用户目标及契约中的目标、交付物、资源范围和验收规则，输出结构化子任务列表。每个节点包含任务 ID（任务标识）、目标、依赖关系和可选验收项。

模型输出进入运行时前会接受以下校验。

- 结果必须包含非空任务列表。
- 子任务数量不能超过契约上限。
- 每个任务必须有目标，任务 ID 不能重复。
- 依赖只能指向已经出现的任务，从结构上避免环和未知依赖。

规划器提示词要求模型不要扩大契约范围，但当前静态校验不会逐项分析每个节点是否越过文件或工具边界。资源权限仍由执行阶段的工具守卫强制判断。

当前调度器按依赖顺序串行推进节点，可以记录 pending（待执行）、running（执行中）、completed（已完成）、failed（失败）和 needs_review（需要复核）等状态。项目尚未实现并行调度和按失败类型配置的自动重试策略。

### 4 任务契约与审批

任务契约使用 Pydantic Schema（数据结构校验规则）检查，主要包含以下内容。

- 任务目标、输入、输出和交付物
- 可读、可写、可执行和禁止访问的资源范围
- 允许、禁止和高风险工具
- 工具调用数、Shell（命令行）执行时长、文件数量和文件大小限制
- 风险等级、审批信息和验收规则
- 流程模式、规划配置和多仓库登记

高风险调用被拦截后，系统会为原始工具名和参数生成绑定信息并创建审批记录。批准具有有效期和一次性消费状态，执行时必须匹配原调用。已经消费、过期或参数变化的批准不能重复使用。

系统通过 checkpoint（检查点）恢复原始调用，不要求模型在批准后重新生成参数。

### 5 运行账本、证据与验收

SQLite（轻量数据库）运行账本保存 run（单次运行记录）、任务节点、审批、证据、checkpoint（检查点）、仓库信息和验收决策。JSONL（逐行 JSON）日志记录关键事件，并对敏感字段、长文本和文件内容进行递归脱敏或摘要处理。

当前日志会记录 `llm_input`（模型输入）事件及消息数量，但不会把完整模型输入原样写入日志。工具参数和模型输出也会经过敏感字段清理或内容指纹处理。

当前验收规则支持四类检查。

- `no_contract_violation`（没有契约违规）
- `file_exists`（目标文件存在）
- `tool_called`（指定工具已调用）
- `tool_not_called`（指定工具未调用）

验收报告绑定 `run_id`（运行标识）、`contract_id`（契约标识）和 `contract_hash`（契约哈希），汇总工具调用、违规、待审批动作及每条验收规则的结果。audited（审计模式）还会比较执行前后的文件基线，识别越界变更和未上报变更。

## 五 两到三分钟口述版

我独立做了一个叫 PactFlow 的智能体运行时。这个项目起源于我对 Agent 落地风险的观察。模型一旦获得文件、命令行和外部 Skill 等工具，错误就可能产生真实环境后果，例如访问范围越界、过程无法追溯，以及模型声称完成但缺少证据。

我把产品定位为契约约束下的透明可控智能体运行时，并在模型和工具之间增加流程治理层。用户任务会先形成结构化契约，里面包含目标、权限、工具策略、审批条件和验收规则。所有工具和动态 Skill 都进入统一网关，调用前检查工具与资源范围。高风险动作需要一次性批准，批准会绑定原始调用并防止过期或重复使用。

在复杂任务上，我设计了 chat（对话模式）、development（开发模式）和 audited（审计模式）。对话模式保留轻量交互，不做任务拆解。开发模式使用模型规划器生成任务 DAG，校验任务数量、标识和依赖关系，规划失败时回退到确定性方案。审计模式再增加文件基线、检查点和变更对账，用于需要更强证据的任务。

技能部分有两套机制。第一套是 Skill Registry（技能注册表）元数据检索，负责在大量技能中找到候选。第二套是 help → run 两阶段调用，负责选中技能后先查看完整说明，再申请执行。高风险技能强制先 help，低风险且可信的技能可以直接申请 run。检索结果和 help 都不会直接授予权限，真正执行仍由契约守卫判断。

最后，系统用 SQLite 保存任务、审批和证据，并根据契约生成验收报告。仓库中有 132 个自动化测试方法，其中 P0（最高严重级别）回归套件包含 15 个测试方法和 26 个具体场景。另有一组 20 个本地合成场景，用于比较直接执行和 help 后再决策两种调用方式。该实验中安全命中率由 50% 提升到 90%，测试口径下的 P0 率由 50% 降到 10%，平均决策耗时增加 23.5%。这组数据验证的是两阶段调用机制，不能解释成生产环境事故率，也不能代表完整契约系统的整体收益。

## 六 高频面试问答

### Q1 为什么做 PactFlow

我关注到 Agent（智能体）获得工具后，错误会产生真实环境后果。仅用提示词提醒模型谨慎，难以形成稳定、可测试的权限边界。我因此把问题拆成执行约束、过程追踪和结果验收三部分，并做成一个可以运行和验证的 MVP（最小可行产品）。

### Q2 产品定位是什么

PactFlow 是契约约束下的透明可控 Agent Runtime（智能体运行时）。它位于模型决策和工具执行之间，通过任务契约、工具守卫、审批状态机、运行账本和验收报告管理 Agent 的完整任务过程。

### Q3 三种模式为什么这样划分

模式数量需要让用户容易理解，同时覆盖明显不同的风险水平。chat（对话模式）解决轻量交互，development（开发模式）解决复杂任务拆解，audited（审计模式）解决需要文件基线和证据对账的场景。具体权限继续由契约配置，避免为每种权限组合再增加一个用户模式。

### Q4 模型规划器和 Codex 展示的执行步骤有什么区别

两者都可以由模型把目标拆成多步。PactFlow 更强调这些步骤进入运行时后的治理属性。计划会形成持久化任务节点，记录任务标识、依赖和状态，并与运行记录、契约和验收结果关联。一般聊天界面中的步骤也能帮助用户理解进度，但不一定等同于业务系统中的持久化任务对象。

我不会声称成熟产品没有任务规划。PactFlow 的差异在于把规划、权限、审批和验收放进同一个可测试流程中。

### Q5 为什么使用 DAG

DAG（有向无环任务图）能表达子任务之间的先后依赖，并让系统定位当前执行到哪个节点。它也便于把失败和验收结果关联到具体任务。当前实现采用依赖感知的串行调度，重点验证流程治理，尚未扩展到并行调度。

### Q6 模型计划如何校验

系统先检查输出结构和任务数量，并确认每个任务都有目标。随后校验任务标识是否唯一以及依赖关系是否合法。依赖只能指向更早出现的任务，因此不会形成环。契约内容会提供给规划模型，但文件和工具权限不会仅靠规划结果判断，执行时仍由工具守卫检查。

### Q7 模型规划失败怎么办

规划结果无法解析或校验不通过时，系统会记录 fallback（回退）事件，并改用确定性拆解。这样可以保留基本可用性，也能在审计记录中看到模型规划失败的原因。

### Q8 计划是否一定由用户确认

当前版本没有完整的计划确认界面。运行时会记录计划已确认并继续执行，代码也预留了 `acknowledge_plan`（确认计划）操作接口。后续产品化可以在开发模式和审计模式增加真正的人工确认、修改和重新校验流程。面试时我会把这一点作为实现边界说明。

### Q9 技能检索和 help → run 是什么关系

它们是两套相互配合的机制。技能检索负责找到合适候选，help → run 负责选中技能后先查看完整说明，再申请执行。

当技能很多或名称不明确时，先使用 Skill Registry（技能注册表）检索。当技能已经明确时，可以直接进入 help → run。高风险技能的完整路径会包含注册表检索、Manifest（能力清单）预览、help 和 run。低风险且可信的技能可以跳过 help，但执行仍要经过契约守卫。

### Q10 Manifest（能力清单）为什么不算第三套机制

Manifest（能力清单）是技能检索之后的轻量预览，属于发现和选择环节。它展示技能的名称、用途、风险和依赖工具，帮助模型判断候选是否合适。

从代码接口看有 manifest、help、run 三种模式。从产品设计看，manifest 归入技能检索和渐进披露，help 与 run 组成两阶段调用。因此对外介绍时应说“技能检索 + help → run”，再解释 Manifest 是检索后的轻量能力卡。

### Q11 技能检索算不算 RAG

当前实现不应直接称为 RAG（检索增强生成）。它采用关键词、词元重合和子串匹配进行元数据排序，没有 Embedding（向量嵌入）、向量索引或语义重排。更准确的表达是基于 Skill Registry（技能注册表）的元数据检索和候选召回。

### Q12 help → run 是否对所有技能强制执行

系统保留了 help → run 两阶段调用，但没有对所有技能统一强制。低风险且可信的技能可以直接申请 run，其他低风险和中风险技能需要先查看能力清单或 help，高风险和关键风险技能必须先读取完整 help。所有路径最终仍要经过工具守卫。

### Q13 来路不明的技能如何控制风险

系统先披露它的风险、可信度和依赖工具，再按风险设置运行门槛。它调用的内置文件和 Shell（命令行）工具会受到 office（工作目录）路径、受限环境、命令解析、任务契约和审批机制约束。

当前动态技能没有独立的操作系统或容器级隔离。经过批准后运行的本地脚本仍可能继承宿主进程权限，因此不能把它描述成完整安全沙箱。进一步产品化时应增加容器隔离、签名校验和供应链扫描。

### Q14 任务契约解决什么问题

任务契约把原本散落在提示词和配置中的目标、权限、工具策略和验收标准放入统一结构。系统可以在调用前校验，在执行后按同一份契约验收，也可以用 `contract_hash`（契约哈希）判断任务期间契约是否发生变化。

### Q15 一次性审批如何防止重复使用

审批记录与具体调用绑定，并包含状态和有效期。工具执行前会原子性消费批准，消费后不能再次使用。参数改变、批准过期或状态不正确都会导致执行失败。checkpoint（检查点）用于恢复原始工具调用，减少批准后重新生成参数带来的变化。

### Q16 审计日志记录了什么

日志记录流程启动、工具请求、契约判断、拒绝、审批、Skill 披露和验收等关键事件。敏感键会被替换，文件内容和模型内容会保存长度与哈希等指纹信息，超长文本会截断。`llm_input`（模型输入）当前只记录消息数量，因此我不会声称系统保存了完整模型输入。

### Q17 如何证明任务完成

系统根据任务契约中的验收规则检查运行事件和实际文件状态，生成 passed（通过）、failed（失败）或 inconclusive（无法确定）结果。当前支持无契约违规、文件存在、指定工具已调用和指定工具未调用四类规则。审计模式还会核对文件变更是否在允许范围内并且被工具事件报告。

### Q18 用户能否手动决定最终验收

运行存储和 ProcessManager（流程管理器）已提供操作员验收接口。当前主运行流程会由 runtime（运行时）根据报告自动写入 accepted（接受）、rejected（拒绝）或 needs_review（需要复核），并自动关闭任务。完整的人工验收界面和交互流程仍属于后续工作。

### Q19 失败后如何恢复

SQLite（轻量数据库）保存运行记录、任务节点、审批和检查点，可以支持未完成审批的重启恢复。当前项目没有任意节点无损回放，也没有按错误类型自动重试的完整策略。准确表述是关键运行状态可持久化，部分中断场景可以恢复。

### Q20 测试和实验数据如何解释

仓库共有 132 个自动化测试方法。P0（最高严重级别）回归套件包含 15 个方法，覆盖 26 个权限、审批、流程、规划器和证据场景。测试方法数说明覆盖了多少自动化检查，但不能单独证明生产效果。面试展示时，我会同时说明场景设计、断言、失败案例和修复记录，其中路径穿越问题就是由回归测试暴露并修复的。

两阶段调用实验使用 20 个本地合成场景，对比模型直接执行和先 help 再重新判断两种方式。安全命中率从 50% 提升到 90%，测试定义下的 P0 率从 50% 降到 10%，平均耗时从 19.33 秒增加到 23.88 秒。

这组实验主要验证 help → run 两阶段披露和重新决策的价值。它没有单独测出模型规划器、一次性审批、文件对账等模块各自贡献，也没有使用生产流量。因此我会把它称为本地合成对照实验，不会称为线上 P0 事故率。

## 七 竞品与差异化表达

### 三十秒回答

Claude Code、Codex 和其他成熟编码 Agent（智能体）已经具备任务规划、权限请求、沙箱或执行监控等能力。PactFlow 没有必要否定这些能力。我的项目重点验证一种流程治理方式，将任务契约、DAG、工具守卫、一次性审批、运行账本和验收报告放入同一条流程，让一次 Agent 任务可以按预先定义的边界执行，并在结束后给出可检查的验收结果。

### 可以强调的差异

- PactFlow 把任务契约作为运行时中的正式对象，权限和验收使用同一份结构化规则。
- 计划节点、审批记录、工具事件、证据和验收结论都绑定到同一次运行记录。
- audited（审计模式）会保存文件基线并进行执行后对账。
- 技能检索、help → run 和执行权限分开处理，候选检索和说明披露不会自动获得运行权限。

### 不应使用的竞品表述

- 不断言 Claude Code 或 Codex 没有 DAG、审计、审批或验收能力。
- 不使用无法核验的行业比例、外部事故和基准数字支撑差异化。
- 不把 PactFlow 描述成已经达到企业合规要求的生产系统。
- 不把实现中的 office（工作目录）路径限制等同于完整容器沙箱。

### 被问到是否只是日志工具

日志只负责记录事件。PactFlow 还会在调用前执行契约判断，在高风险动作处管理批准，并在结束后按验收规则判断结果。它的价值来自约束、记录和验收之间的关联。当前验收规则还比较基础，因此更准确的定位是可运行的流程治理 MVP（最小可行产品）。

## 十 简历精简版

- **产品定位** 面向 Agent（智能体）工具越权、过程难追踪和结果难验收问题，独立设计并实现契约约束下的透明可控智能体运行时，以 chat（对话模式）、development（开发模式）和 audited（审计模式）平衡交互效率与任务风险。
- **工具与 Skill（技能）调用** 将内置工具和动态技能接入统一守卫，设计 Skill Registry（技能注册表）元数据检索与 help → run（先查看说明，再执行）两阶段调用。检索负责发现合适能力，高风险技能必须读取完整说明后再申请执行，最终权限由任务契约和工具守卫判断。
- **流程层设计** 引入模型规划器生成结构化任务 DAG（有向无环任务图），校验任务数量、标识和依赖关系，支持依赖感知的子任务编排、确定性回退、SQLite 状态持久化及审计模式文件变更对账。
- **契约治理** 将资源权限、工具策略、审批条件和验收规则结构化，落地统一工具网关、一次性审批、过期与重复使用防护，并生成绑定运行记录和契约哈希的验收报告。
- **效果验证** 建立 132 项自动化回归测试，P0 套件以 15 个测试方法覆盖 26 个具体场景。本地 20 个合成场景实验中，两阶段调用将安全命中率由 50% 提升到 90%，测试口径下的 P0 率由 50% 降到 10%，平均决策耗时增加 23.5%。

## 十一 快速记忆卡

**一句定位** 让 Agent（智能体）在契约边界内完成任务，并用运行证据判断结果。

**三个模式** chat 保持对话效率，development 负责模型规划，audited 增加基线和对账。

**技能两套机制** Skill Registry（技能注册表）检索负责找技能，help → run 负责先看说明再执行。

**验收范围** 无违规、文件存在、工具已调用、工具未调用。

**测试口径** 132 个自动化测试方法，P0 套件 15 个方法和 26 个场景。

**实验口径** 20 个本地合成场景，验证 help → run 两阶段调用，不代表生产事故率或完整系统收益。
